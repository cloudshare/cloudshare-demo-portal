Executive Read

The highest-leverage refactor is to deepen the active ExamAttempt runtime lifecycle module. Today, callers must remember a scattered sequence: settle completion, reload state, check entitlement, correlate environment, touch the clock, record diagnostics, and then perform the requested action. That hidden ordering is part of the interface, and it is duplicated across candidate-facing and admin-support paths.

1. Deepen ExamAttempt Runtime Lifecycle

Recommendation strength: Strong

Primary seam: Candidate runtime operations

Files

  • src/api/enter.ts
  • src/api/suspend-resume.ts
  • src/api/candidate-portal.ts
  • src/api/candidate-lab.ts
  • app/api/heartbeat/route.ts
  • src/domain/exam-clock.ts
  • src/domain/exam-attempt-completion.ts

Problem

The clock module has useful depth, but the lifecycle interface around a current ExamAttempt is shallow. Multiple callers must know when to reconcile completion, reload status, validate access, record completion diagnostics, and proceed. This lowers locality and makes runtime bugs likely to be fixed in one path but missed in another.

Solution

Introduce a deeper runtime lifecycle module whose interface speaks in candidate-facing operations such as enter, suspend, resume, heartbeat/status, and read-current-attempt. Keep ExamClock as the lower-level implementation detail behind that interface.

Benefits

Leverage improves because tests and routes exercise the same lifecycle interface. Locality improves because completion settlement, status transition rules, and diagnostics ordering live in one implementation rather than several route handlers.

2. Retire or Quarantine Legacy Simulator Flow

Recommendation strength: Strong

Primary seam: Active Certalis/Helios lifecycle

Files

  • src/composition.ts
  • src/integrations/genesys/*
  • src/integrations/kryterion/*
  • app/api/exams/eligible/route.ts
  • app/api/exams/book/route.ts
  • src/api/demo-control.ts
  • src/domain/entitlement.ts
  • src/domain/exam-attempt.ts

Problem

The retired Genesys/Kryterion framing is still active in composition, config, routes, demo control, tests, and vocabulary such as booked and Kryterion clock. The deletion test shows it is not merely dead code: deleting the retired adapters would still break route surfaces.

Solution

Choose one path: remove the retired flow completely, or quarantine it behind an explicit demo-only compatibility module with no candidate-facing route surface. The current Certalis/CloudShare lifecycle should be the interface most modules can see.

Benefits

Locality improves because lifecycle language stops being split between current and retired concepts. Leverage improves because scheduling, launch, and demo reset can be tested against the same domain vocabulary used by the product.

3. Make DiagnosticLogEntry the Only Support Source of Truth

Recommendation strength: Worth exploring

Primary seam: Support Diagnostics

Files

  • src/domain/diagnostic-log.ts
  • src/domain/support-log.ts
  • src/api/support-workbench.ts
  • src/web/support-log-table.tsx
  • src/api/admin-monitoring.ts
  • src/domain/admin-monitoring.ts
  • prisma/schema.prisma

Problem

DiagnosticLogEntry is already the deeper module: it has first-class anchors, redaction, append/query, and useful indexes. Legacy Support Log and Support Workbench remain shallow parallel surfaces, while Session Monitoring also reaches into diagnostics for forensic details.

Solution

Use DiagnosticLogEntry as the support evidence seam. Retire or demote Support Log/Support Workbench to internal evidence, and narrow Session Monitoring to current ExamAttempt queues plus compact operational facts.

Benefits

Locality improves because support filtering, redaction, correlation, and pagination concentrate behind one module. Session Monitoring becomes easier to evolve because it no longer has to understand forensic event semantics.

4. Deepen Route Workflow Interfaces from Composition

Recommendation strength: Worth exploring

Primary seam: Workflow dependencies

Files

  • src/composition.ts
  • app/api/heartbeat/route.ts
  • app/api/exam/score/route.ts
  • app/api/admin/diagnostics/attempts/[examAttemptId]/route.ts
  • src/api/admin-exam-attempt-diagnostics.ts
  • src/web/admin-console.tsx
  • src/web/admin-console-state.ts

Problem

Composition is useful as a boot root, but shallow as an interface because routes receive the whole world. Some Next routes are thin framework adapters, while others construct CloudShare adapters and perform workflow reconciliation directly. AdminConsole has the same issue at the UI level.

Solution

Keep composition as the single boot implementation, but expose deeper workflow dependency modules: candidate scheduling, runtime lifecycle, support diagnostics, admin authoring, demo control. Standardize Next routes as cookies/session/body adapters over framework-agnostic handlers.

Benefits

Leverage improves because each route and test learns a smaller interface. Locality improves because CloudShare adapter construction, support refresh, and workflow policy move out of route files and into named modules.

Top Recommendation

Tackle Deepen ExamAttempt Runtime Lifecycle first. It is the most central module for the platform direction: certification, sales demonstrations, TMS flows, and broader CloudShare automation will all need a reliable way to answer “what is the current Customer-owned CloudShare runtime state, and what operation is allowed next?” It also creates a natural place to retire old booked/Kryterion vocabulary without mixing that cleanup into every route.
